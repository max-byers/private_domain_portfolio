# iprescribeexercise.com

Coded static site for the `iprescribeexercise.com` domain in `private_domain_portfolio`.
Content is never synced/cached into this folder — `build_site.py` and `publish.py`
both read the domain's CSVs live on every run
(`private_domain_portfolio/iprescribeexercise.com/iprescribeexercise_posts.csv` and
`iprescribeexercise_pages_content.csv`).

## Build

`build_site.py` renders the complete review site (every post/page regardless of
date) from the CSVs plus `iprescribeexercise_site_structure.txt` (permalink/category
tree — 4 categories: joint-specific-pain, reading-the-warning-signs,
recovery-and-rehab, smarter-training-approach). Run `python build_site.py` with no
arguments for this. Tracks its own output in `.build_manifest.json` so a rebuild can
safely remove files a prior run created without touching `reference/`, `images/`
originals, or anything else in the folder.

## Scheduled publishing

Static, FTP-hosted site, no server logic, so a post's `post_status`/`post_date` (or
a page's `page_status`/`page_date`) can't gate access to a file already sitting on
the host — the file simply can't exist there yet. `publish.py` handles this.

Unlike a from-scratch regex-patching approach, this site's `build_site.py` was
written with an `as_of` parameter built in: `build(output_dir, as_of=...)` filters
posts/pages to only what's due *before* rendering anything, so every surface
(homepage, blog index, category listings, individual articles, sitemap.xml) is
generated by the exact same code path as the complete build, just fed a smaller
dataset. `publish.py` is a thin wrapper: it imports `build`, `is_due`, `read_rows`,
`slugify`, and the CSV path constants directly from `build_site.py` (same site
folder, not a cross-site import) and calls `build(output_dir=DEPLOY_DIR, as_of=...)`.

Flags: `--build` writes `_deploy/` (git/deploy-ignored build artifact, rebuilt fresh
each run). `--upload` FTPs `_deploy/`'s contents to the live host (credentials from
`hosting_accounts.csv`, looked up by domain). `--commit` flips `post_status` from
`future` to `published` in the source CSV for posts released this run (only takes
effect alongside `--upload`). No flags = report-only, listing due/not-due status.
`--as-of YYYY-MM-DD` overrides "now" for testing.

Quirks specific to this domain:
- The domain's very first post ("My shoulder was not asking for more discipline")
  and all 6 pages already carry `post_status`/`page_status` = `published` in the
  source CSVs, matching the site's launch date (17/08/2026) — `is_due()` treats
  `status == "published"` as unconditionally due regardless of `as_of`, so these 7
  items are always in `_deploy/` no matter how early an `--as-of` you test with.
  There's no genuine "zero content due" state for this domain once its launch date
  has passed — the launch-day post and the pages are permanently live from day one.
- The homepage's "latest posts" widget shows up to 3 due posts ranked by
  `post_date` descending (fewer if fewer are due — e.g. just 1 today). The 4
  homepage "Guides" cards and the footer's "Recent Guides" list both draw from a
  fixed set of 4 of the 6 pages (`featured_page_slugs` in `build_site.py`); since
  all 6 pages share one `page_date`, this selection isn't actually date-sensitive
  in practice, just a fixed editorial pick.
- A category with zero currently-due posts still gets its listing page (with an
  empty `<ul>`) and still appears in nav pills/footer — not hidden entirely. This
  is a known simplification, not a bug; revisit if a category could plausibly stay
  empty for a long stretch after launch.

Tested 2026-08-18 at three `--as-of` points: today-equivalent (1 post + 6 pages due,
20 posts correctly absent from every listing/nav/sitemap surface), a partial state
(8 posts + 6 pages due — verified category listing counts, the latest-posts widget
ranking, and sitemap entry count all matched expected numbers exactly), and a
far-future state (all 21 posts + 6 pages due, matching the complete build's output
counts exactly). `--upload` not yet tested against real credentials — no hosting
account exists for this domain yet in `hosting_accounts.csv`.
